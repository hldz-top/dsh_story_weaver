# Writing runner

## Scope and ownership

[`WritingRunner`](../../src/writing-runner.ts) coordinates researched settings, outlines, bodies and continuity through DSH native child execution. The [writing service](writing-service.md) owns authoritative documents and applied heads; the [run store](writing-runs.md) owns immutable requests, stage attempts and saved raw output. The runner owns only admitted in-process work and cancellation. It does not create an AgentLoop, register a provider adapter or open a separate database. A stage inherits the parent model unless `writingModel` names that stage's host provider and model.

The package root exports `WritingRunner`, `StageDeliveries`, `registerStageDeliveryProjection`, `openRunStore`, `openWritingService` and their declared service/run types. The plugin provides `ctx.story` and `ctx.storyRunner`, and mounts [writing tools](writing-tools.md) as Cordis effects. Tool callers use those public tools; implementation references below point to the source modules that own exact types.

## Invocation API

`new WritingRunner(ctx, service, runs, limits, deliveries)` receives the existing Context, open writing service, open run store, explicit `RunExecutionLimits` and a `StageDeliveries` publisher constructed with `(ctx, service, runs, previewDirectory)`. The plugin registers the stage-delivery projection before constructing the runner. One awaited disposal effect cancels and awaits the runner, then drains the run store and writing service; independent asynchronous disposers would not guarantee that order. Each operation derives its actor from the actual `ToolExecution` Session and filesystem workspace. A supplied novel ID cannot override ownership.

| Method | Input and observable result |
| --- | --- |
| `start(exec, input)` | `StartWritingInput` contains `novelId`, current `briefArtifactId`, novel-scoped `requestId`, explicit `settingsRoots`, `chapterCount`, inclusive `fromChapter`/`throughChapter`, and the write/update mode. The runner supplies `revision: null` and snapshots both execution and service limits. Returns terminal `WritingRun` metadata after owned native work settles. |
| `revise(exec, input)` | Accepts the run-store input without `executionLimits` or `serviceLimits`, requires `mode: 'revise'` and `revision: {baseArtifactId, instructions}`. Revises only that exact current applied settings dimension, book outline or chapter outline, then returns terminal metadata. The request retains its explicit chapter scope, but does not authorize downstream writing. |
| `resume(exec, runId, retryUnknown)` | Checks the current service limits against the saved snapshot before changing progress or retry authorization, then resumes retained progress in the owning workspace using captured execution settings. An already active in-process invocation shares its completion. An outcome-unknown attempt requires explicit `true`; saved successful outputs are reused. |
| `stop(exec, runId)` | Cancels an active run and awaits it, or marks an inactive running/interrupted run stopped. An already terminal run is returned unchanged. |
| `close()` | Prevents further admissions, aborts owned active runs and awaits both admitted starts and active completion. It does not close either storage owner. |
| `runs` | Read-only reference to the run-store API for workspace-authorized metadata queries and explicit output reads. |
| `limits` | Constructor-supplied execution settings; new runs persist their own snapshot. |

The current brief must equal the request's `briefArtifactId` at admission and before each stage attempt. Settings roots must form a valid enabled dependency plan. `story_write` refuses existing stale settings or manuscript state and asks for explicit update intent. The run store enforces request identity, valid chapter ranges, one unfinished run per novel and finite attempt/output budgets. A repeated request with different fields rejects; a completed unchanged request reuses its result while current admission requirements still hold.

Admission, ownership and invalid-input failures reject the call. Once execution starts, a stage or domain failure produces retained `status: 'failed'` and its reason; cancellation produces `stopped`. Failure to persist terminal cleanup can still reject. A returned run is therefore not necessarily completed: callers must inspect its status and error.

## Automatic writing

1. Expand only the requested settings roots through the real catalog's dependency closure. A new run drafts those dimensions in dependency order and does not use layer width to split that draft. A run that already started the older per-dimension path keeps it. Independent dimensions in one layer of that path overlap up to `dimensionWidth`, which is `maxParallelStages` only. That width does not read `settingsCandidateCount`, so the default count of 1 does not reduce the width to 1.
2. A new settings layer makes three model requests. The draft returns `{ dimensions: [{ code, body }] }` for every code that still needs text. The consistency review stays on a subagent and returns `{ issues: [{ dimension, kind, quote }] }`, naming only conflicts and gaps. The repair returns the same draft shape for only the dimensions named by that review. When `estimateSettingsBatchBytes` exceeds the run's `maxOutputBytes`, each of those requests is split into groups of 4. The captured JSON is also rejected when its UTF-8 size exceeds `maxOutputBytes`. `settingsCandidateCount` is how many comparison drafts to capture. The default `1` keeps a single draft. A value above 1 captures that many drafts and applies the first valid one. It does not change how many dimensions run together and it does not cap parallelism. On the per-dimension fallback, the same count is how many candidates one dimension generates on its first pass: one candidate keeps the historical `candidate/<n>` key, more than one uses `candidate/0/n/<index>`, and a later repair stays a single candidate. Before the draft, and whether or not research planning runs, the runner calls the host's official `web_search` and `web_fetch` once. A used result carries excerpts into the draft. Unavailable tools and quota or billing failures continue from the brief and do not fail the layer. Any other retrieval failure stays fail-close and no draft is saved. Research planning and research children stay off when research is disabled or the remaining call budget is below `researchBudgetFloor`. A local not-needed research plan is still recorded so each dimension can be stored, and a missing model research child is not a settings failure. Official settings retrieval does not use that skip. The host then applies the exact drafted text. A blocking review with `maxRepairAttempts` of 0 stops without the repair. Imported text is still not regenerated. After the collection is applied, the novel stores `{ briefSha256, roots, artifactId }`. A later run with `reuseSettingsSnapshot` on (the default) and the same brief text and roots skips settings and starts at the outline. One changed character in the brief changes the hash and the snapshot does not apply. Turning the flag off does not use the snapshot.
3. Generate, review and apply the book outline for the explicit total chapter count in one pass.
4. Generate and apply every requested chapter outline before any body. Outlines in that pass read only snapshots of chapters already applied before the requested range. Independent outlines overlap up to `chapterBatchWidth` (at most 3, and never above `maxParallelStages`).
5. Write bodies in batches of that same width. Each chapter in a batch reads the outline plus reviewed continuity snapshots of chapters applied before the batch. It does not read an unfinished chapter from the same batch. After the reviewed body and continuity are applied together through one queued novel update, one short stage extracts a compact continuity snapshot and a review must pass before that snapshot is stored. The next batch then reads it.
6. Verify each requested chapter is applied and current, with a reviewed snapshot, before marking the run completed.

Every new manuscript research stage also captures necessity before retrieval. Planning attempts count toward `maxRunAttempts`. Graded stages use the deadlines in the configuration table; research execution keeps `stageTimeoutMs`. An existing saved research attempt retains its original prompt and is not silently replaced. The pipeline reuses current matching settings, outlines and applied chapters. A requested range does not silently expand to rewrite chapters outside it; its required preceding context must exist. Plans remain plans: final continuity and fulfilled obligations require evidence in actual prose. [Manuscript admission](manuscript.md) owns exact input/head checks and atomic chapter publication.

`story_update` follows the same dependency order, rebuilding affected work within the requested scope while preserving immutable history. `story_revise` instead adopts only its named upstream replacement, records `revisionOf`, and stops. Descendants retain their existing text and IDs and expose stale inputs until an explicit update is requested. Settings and manuscript artifacts each have immutable identity; do not infer revision lineage from an incrementing numeric artifact revision.

## Typed review and bounded repair

### Output admission and repair

Every host rejection of a model-produced value throws one type, `StageValidationRejection` ([`src/stage-rejection.ts`](../../src/stage-rejection.ts)), carrying a specific, model-actionable message. The runner repairs only that type, within `maxRepairAttempts`, in every loop: research planning (`<key>/planning/<n>`), the research child (`<key>/repair/<n>`), settings and manuscript candidates (`…/candidate/<n>`) and reviews (`…/review/<n>`). Attempt 0 receives no rejection, so first-attempt prompts stay byte-identical for resumed runs; replacements receive the previous rejection as `validationError`. Oversized model artifacts are rejected before storage with their byte count and the limit. Provider errors, refusals, truncation (`max-tokens`), cancellation, stage request budgets, tool-scope violations, raw output above the run's output byte limit, store conflicts and integrity failures are never repaired. A published execution timeout on a graded stage is recorded `unknown` with `retryAuthorized` set, and the same key is replaced once. A second consecutive timeout leaves `retryAuthorized` false and fails the run. `story_stop` aborts the run immediately and does not authorize that replacement. An unpublished timeout, a timeout of research execution, and any failure that is not an execution timeout stay fail-closed. Native `structured_output` schema rejections are returned to the model inside the same child turn before host admission; malformed provider JSON and a missing result retry the same key. Exhaustion messages end with the last rejection.

Native child structured capture uses the [published stage schema](stage-execution.md#writing-stage-schema-publication). The canonical [stage parsers](stage-output.md) additionally check stage identity, exact input references, required scenes/checks, source quotations and obligation evidence. Structural native capture is not domain approval.

Each local candidate or review repair loop allows one initial attempt plus at most `maxRepairAttempts` replacements. Settings collection repair has its own bounded loop; the global `maxRunAttempts` separately caps all retained attempts, including research and authorized replacements. These are distinct limits, not one total retry count.

A captured value is saved before domain admission. A typed candidate or review rejected with `StageValidationRejection` supplies that message to a distinct repair attempt. Blocking review feedback supplies the exact previous candidate and review as readable artifacts. Repair prompts request the complete replacement while preserving unaffected facts and prose; they do not authorize overwriting prior content. Non-output errors such as research failure, storage failure or changed inputs are not converted into empty candidates or arbitrary automatic retries.

A stage whose child ends with a malformed provider response (`stage-malformed` in [stage execution](stage-execution.md)) has a known failed outcome: a response arrived, but DSH could not decode it. The runner records that attempt as failed and retries the identical request under the same stage key, up to `maxRepairAttempts` replacements for that stage. Each replacement is a durable attempt counted by `maxRunAttempts` and starts a new native child, which repeats the stage's reads, model requests and, for research, web calls. Exhaustion fails the run with the malformed-response message; an explicit resume replaces the failed attempt under the same bound. Because the key and request stay the same, a resumed run replays the saved path instead of re-executing the stage. A structured value captured before a later turn error is not treated as malformed.

A stage whose child turn ends normally without returning its structured result (`stage-missing-result`), for example because the model answered in plain text instead of calling `structured_output`, follows the same rule: the attempt is recorded as failed, not unknown, and the identical request is retried under the same stage key up to `maxRepairAttempts` times. When those automatic retries are exhausted the stage fails and the run ends `failed` with an explicit message naming the stage key and the number of retries, for example `Writing stage turn ended without returning its structured result; stage body/1/candidate/0 failed after 1 automatic retry`. The run never continues past a stage without its structured result. `maxRepairAttempts: 0` disables the automatic retry.

A provider refusal (`stage-refused`) or an output-length cut-off (`stage-truncated`) is also a known outcome: a response arrived but cannot be used. The runner records the attempt as `failed` with an explicit `failureKind` of `refused` or `truncated`, saves no output and no candidate, and fails the run with the stage's explicit message. It does not retry automatically, because an identical request would meet the same policy or length limit; an explicit resume replays the identical request without `retryUnknown`. `story_get_run` and `story_list_runs` report `failureKind` on those attempts; other attempts omit the field.

Prompt versions before 7 give the configured chapter-total range to stages that write or review a book outline, chapter outline or body. Version 7 gives that numeric range only to the body and its review. The body aim is the configured minimum (3000 under the acceptance profile), not the midpoint of the range. Outline stages are not given the number as a planning budget. Settings generation and review prompts use the catalog kind of the requested dimension. A [classification dimension](../specs/story-writing-plugin/CONTEXT.md) (`enum_single` or `enum_multi`) records its labels, brief grounds and constraints for later stages rather than invented world detail. The service rejects a new classification candidate that exceeds the [settings size bound](stage-output.md#settings-dimensions), and the runner treats that rejection as invalid output for repair.

Prompt version 6 appends writing-quality sentences to the existing stage instructions. Version 8 is what new runs record; it keeps the version 7 sentences. Free-form settings that define people state a present want, a limit and a reusable relationship fact; classification dimensions stay labels, grounds and constraints. Book outlines state each arc's starting want, pressure and ending stance, and each chapter's immediate want and risk. Chapter outlines name the choice, motive and cost in `scene.action` and refuse events that contradict applied continuity or current knowledge. Bodies show that want inside the choice and do not invent knowledge, tools or injuries. Continuity records only changes the reviewed prose supports and fulfills an obligation only when the prose performs it. Reviews write `issue.message` as one repair step. Thin motivation, wording and taste stay `style` / `advisory`. Blocking categories stay the existing set: a missing required event, a settings or persona contradiction, a cross-chapter continuity conflict, or a host-measured length violation. Author revisions apply `task.revisionInstructions` without inventing a new plot. The same `maxRepairAttempts` loop still bounds generation, review and repair. Versions 1–6 rebuild their previous prompt bytes. Version 7 is the first version that omits outline `targetWords`, the scene-allocation sentence, and the outline acceptance-range line. These sentences do not add a schema field or a new acceptance gate.

Prompt version 7 reviews receive `task.paragraphs`, the host re-split of the candidate body, and must cite `{ paragraphId, problem }`. g4 and g7 reviews instead return the fixed checklist in `task.checklistItems`. Each settings candidate line counts its own fails and holds its own candidate. A line may repair again only when its new fail count is less than or equal to that line's previous fail count. A higher count stops that line and applies the candidate it already holds, including when that candidate still has fails. A fail count of zero applies the candidate that line just reviewed. A line never reads another line's fail count, and concurrent dimensions do not share this state. One candidate keeps `candidate/<repair>`. More than one keeps `candidate/<repair>/n/<index>` for that line's later repairs as well. If the budget ends while the line's count is still positive and has not risen, that held candidate stays unapplied. When no line can be applied, the run stays review-blocked.

Prompt version 8 outline, chapter-outline, body, and continuity reviews use that same decision with one stricter stop: a later round whose blocking-issue count is not strictly lower applies the candidate already held and does not spend the remaining repair attempts. A count of zero still applies the candidate just reviewed. A lower positive count may repair again. The held review stays blocking; the manuscript record stores `convergence` with that review id and fail count so continuity can be derived and the chapter can be applied. Host length and unfulfilled obligations still refuse application. g4 and g7 keep the original rule and still apply a held candidate only when the checklist fail count rises. Versions before 8 keep exhausting a non-improving outline or manuscript review.

Version 8 review admission rejects two model outputs before they can block a candidate. `check.summary`, `issue.message`, and `evidence.problem` must contain a Han character. A blocking `completeness` or `obligations` issue must set `briefQuote` to a verbatim excerpt of the creative brief; the host rejects the review when that excerpt is missing or is not in the brief. Consistency, continuity, length, and style issues do not use `briefQuote` to state a new requirement. The prompt states both rules. Versions 1–7 keep their prompt bytes and published schemas; only version 8 publishes `briefQuote`. Readback of a stored review does not repeat these admission checks. Host-synthesized settings reviews are not model output and are not subjected to them.

The host assembles and counts each body after generation and every repair. The configured inclusive word range is a hard blocker independent of model review. A version-7 body prompt states the range, the Story counting rule, and an aim at the configured minimum. A body review states that a host-measured count inside the range is not a length defect. A length repair receives the host count, the violated bound and distance, per-scene counts and that aim, and a repair instruction to condense or expand across all scenes instead of preserving passage wording. Versions before 7 still aim at the midpoint and still state the range to outline stages. Required-event omissions, settings or persona contradictions and cross-chapter continuity conflicts block application. The host word-count check blocks on its own. Style and AI-tone findings stay advisory: from prompt version 7 the review receives a density grade (`hint`, `notice`, or `heavy`) and a dash or enumeration comma does not fail the chapter. Dialogue stays outside the scan. Unfulfilled continuity obligations also block. Exhaustion retains available candidates, reviews and raw output and ends the run as failed without advancing the next chapter.

A version-7 body reads the book outline and the chapter outline through a feed: this chapter's title, purpose or through-line, obligation descriptions, and each scene's purpose and action. Constraints, state notes, word targets and the rest of the book are not in that feed. Other body inputs stay stored text. Reviews still read the prose view.

## Durable attempts and model-visible data

Before native startup, `prepareAttempt` persists the exact prompt, input digests, output schema and original parent Session. A stage that only reads those inputs and writes text (research planning, settings and manuscript candidates including the body, and their repairs) then calls the host `ctx.llm` once. The runner inlines the exact input text, streams one request on the parent model unless `writingModel` names that stage's provider and model, and aggregates the assistant text. It writes that model-visible prompt and the raw reply into the current Session workspace under `previewDirectory/generation-audit/<runId>/<attemptId>/` before admitting the stream and after the reply arrives. The stored attempt prompt stays the versioned instruction text, so a resumed run still matches it. The generation receipt is a unique id stored in `childSessionId`; it is not a subagent Session.

Review, citation repair, and research stay on the native child. Those stages call tools such as `story_read_artifact`, research tools, or web tools. Their `onStarted` callback saves the actual child Session before the first model stream. Domain source documents for those stages are still read through logged bounded `story_read_artifact` calls.

After execution settles, the runner saves `JSON.stringify(structured)` as immutable raw output, then parses and publishes admitted domain artifacts. An attempt marked succeeded proves durable raw output only. Research uses the actual logged start receipt and persisted native web results, checked against the original child lineage. Saved source excerpts remain untrusted data. [Research admission](research-stage.md) and [native execution](stage-execution.md) own those checks.

Run queries omit prompts, response schemas and long raw outputs. `story_read_run_output` explicitly reads retained raw output in bounded Unicode pages with exact digest/size metadata. `story_preview` projects a domain artifact into its full versioned Markdown representation. Neither a metadata result nor an excerpt proves a complete document was read; callers follow the reader through `eof`.

## Cancellation and recovery

Stop combines the calling tool's signal with a run-owned controller. Parallel settings work settles before failure is finalized, and every published native child is disposed before its executor returns. Cancellation checks and service-owned queued version checks prevent late results from being adopted after stop. Earlier applied work remains visible; cancellation is not a transaction rolling it back.

Reopening the run store marks persisted running runs interrupted, reconciles exact saved output, and marks unsaved active attempts unknown. It does not launch children. Explicit resume checks ownership and the current brief, reuses completed attempts, and requires permission to replace unresolved attempts. Unknown describes missing durable outcome, not proof that no provider execution or cost occurred.

Execution and run-store limits remain captured. Each new run also records seven `serviceLimits` fields: `maxArtifactBytes`, `maxReadChars`, `maxResearchQuestions`, `maxResearchCalls`, `maxResearchSources`, `maxEvidenceChars` and `maxResearchLogEvents`. Resume compares all seven, the service chapter bounds and, as the tenth item, `aiToneBlocking` before calling the durable resume operation. `aiToneBlocking` is recorded in `executionLimits` on every run from prompt version 5 onward: a differing current value is refused like the other limits, a version-5 or later record without it is refused as corrupt, and runs from prompt versions 1 to 4 have none, compare as off and resume with advisory AI tone. A mismatch rejects with `run-limits`, naming every differing key in the readable text and in a final JSON line `{"code":"run-limits","mismatched":[{"key":…,"saved":…,"current":…}]}`, without changing stopped status, saved progress or unknown-attempt retry authorization. Restore the original limits to resume; no default or relaxed budget is inferred. When a run recorded `writingModel`, `researchEnabled` or `researchBudgetFloor`, resume compares that recorded value with the live plugin limits. A run that left any of those fields absent is not a mismatch and is not back-filled: it keeps the parent model, still researches, and uses floor 1. Changed source versions or incompatible saved attempt requests still reject.

The run store migrates plugin-owned version-1 novel-run records to version 2 without changing the host domain generation. Migrated runs carry explicit `serviceLimits: null`; their metadata and saved output remain readable, but they cannot resume or prepare new attempts. Stop an unfinished legacy run and begin a distinct request under explicit current limits. [Run-store migration](writing-runs.md) owns admission and retained-history details.

## Configuration

[`Config` and plugin application](../../src/index.ts) own defaults and validation. The plugin loads only when the resolved `@deepseek-ai/dsh-subagent` package is exactly `0.2.2-rc.3` and the live service has `startActivation` without `start`. That package version is the documented `package.json` export of the resolved module; it is not a DSH application version, and method names alone do not identify a release. The required host services are `storageDomain`, `tools`, `fs`, `llm`, `subagents`, `agents`, `sessions`, `sessionPersistence` and `sessionProjections`. Direct text stages call the injected `llm` service; tool stages still use `subagents`. The native `present` tool must be available in the actual calling Agent scope; start, revise and resume check availability before admitting work. Deployment must configure the verified in-process spawn provider and native web tools/providers used by research; a nonblank provider name alone does not verify its implementation. Model routing and subscription stay on the DSH host. This plugin registers no provider adapter.

| Field | Default | Meaning |
| --- | --- | --- |
| `stageProvider` | `spawn` | Configured native in-process subagent provider; not an LLM model/provider override. |
| `writingModel` | `inherit` | `inherit` uses the parent Agent's model for every stage. A map may set `planning`, `review` and `body` to `inherit` or `{ provider, model }`. Omitted roles inherit. Planning covers outlines, research planning and continuity snapshots. Review covers reviews and citation repair. Body is the chapter prose. Other stages, including research execution, stay on the parent route. `opencode-go` is rejected. This plugin registers no provider adapter and does not substitute another channel when the named provider is absent. |
| `researchEnabled` | `false` | Research planning and research children stay off until a deployment sets this true. While it is false, each stage records a not-needed plan and continues. A missing research result is not a settings-layer failure. Official settings retrieval is independent of this switch. |
| `researchBudgetFloor` | `1` | When research is enabled and remaining native web-call slots are below this nonnegative floor, research planning and research children are skipped the same way. Settings official retrieval still runs. An unavailable provider or a quota or billing failure continues from the inputs and does not fail settings. |
| `maxDelegationDepth` | `2` | Positive absolute native child depth cap. |
| `maxStageRequests` | `96` | Positive model-dispatch allowance per native child, including retries. |
| `stageTimeoutMs` | `600000` | Deadline in milliseconds for research execution, including startup and cleanup; cancellation still waits for owned work to settle. Maximum `2147483647`. Graded stages use fixed deadlines instead: planning `600000`, settings and continuity-snapshot candidate `600000`, the first book-outline, chapter-outline, and continuity candidate (`book-outline/book/candidate/0`, `chapter-outline/<n>/candidate/0`, `continuity/<n>/candidate/0`) `1200000`, review `1200000`, body generation `1800000`, repair `900000`. A settings batch draft and its comparison drafts stay on the 600000 candidate deadline. Later outline and continuity candidates (`/candidate/1` and up) stay on the repair deadline. A continuity snapshot's first candidate stays at 600000 because it is a short extraction, not the long outline document. A batch consistency review is a review stage. A targeted settings repair and a draft output-admission repair are repair stages. |
| `maxRepairAttempts` | `2` | Nonnegative replacements per local repair loop. The same budget covers output-admission repair: a review or candidate the parser rejects (for example one misquoted citation) is regenerated with the parser's message as `validationError`. With `0`, a single rejected quote fails the run. Research planning decisions and research children use the same budget for their replacements. Business repairs (blocking review, chapter length, unfulfilled continuity) share a candidate loop's budget with that loop's output rejections. This budget does not authorize a second graded-stage execution-timeout retry. |
| `maxParallelStages` | `3` | Positive width for independent settings dimensions within one dependency layer of a run that already started the per-dimension path. `settingsCandidateCount` does not change it. A new three-request batch does not use this width to split the draft. |
| `settingsCandidateCount` | `1` | How many comparison drafts a new settings batch captures. The default `1` keeps a single draft. Above 1, that many drafts are captured and the first valid one is applied. A resumed per-dimension run generates this many candidates on each dimension's first pass and still runs `maxParallelStages` dimensions together. New runs record `1`. A run stored before the field existed uses 1. The value is not a concurrency width. |
| `reuseSettingsSnapshot` | `true` | When a stored snapshot has the same brief sha256 and the same roots, skip settings and start at the outline. A one-character brief change does not match. Not an execution limit. |
| `maxRunAttempts` | `512` | Positive retained attempt cap per run. |
| `minChapterWords` | `3000` | Inclusive assembled-body minimum using the [Story counter](body-text.md#counting). |
| `maxChapterWords` | `5000` | Inclusive assembled-body maximum; cannot be below the minimum. |
| `maxArtifactBytes` | `1048576` | Positive UTF-8 limit for a domain artifact; also supplied as the run store's raw-output and revision-instruction limit. |
| `maxReadChars` | `4096` | Positive maximum Unicode code points per artifact/raw-output tool page. |
| `previewDirectory` | `.dsh-story` | Normalized Session-relative directory; empty, dot, parent, whitespace-padded, backslash, colon and control-character segments reject. |
| `maxResearchQuestions` | `12` | Positive per-plan question limit. |
| `maxResearchCalls` | `12` | Positive native web-call reservation limit per plan. |
| `maxResearchSources` | `24` | Positive admitted source-count limit per research result. |
| `maxEvidenceChars` | `16000` | Positive bounded evidence/finding text allowance under the [research rules](research.md). |
| `maxResearchLogEvents` | `2048` | Positive logical Session-event admission limit. |

All numeric limits require safe integers; all are positive except `maxRepairAttempts`, which permits zero. `stageProvider` must be nonblank. Run execution settings, run-store size/attempt limits and the seven writing/research service limits are copied into each new run. The mounted service enforces its configured limits; a retained run can resume only when those service limits and chapter bounds match its snapshot. These limits bound observed requests and data, not provider currency charges.

## Stage presentation

[`StageDeliveries`](../../src/stage-deliveries.ts) builds or verifies the complete exact-version Markdown file, executes the registered native `present` tool as one `tools.execute` batch under the parent Agent, checks its committed `deliverables/presented` event and awaits Session flush. Dependent stage work continues after this publication succeeds; independent settings stages may overlap. A denied tool, changed preview, missing event or flush failure remains a run failure rather than an empty successful delivery.

Automatic publication selects exactly four artifact kinds: the complete settings collection (`settings`), `book-outline`, `chapter-outline` and `body`. Eligible persisted candidates and repaired versions can be shown before application; a full preview is not approval. A fresh three-chapter run without repairs produces eight automatic documents: one settings collection, one book outline, three chapter outlines and three bodies. Research plans/results, `settings-dimension`, reviews and continuity retain their durable records and explicit readers, but receive no new automatic publication. Rejected raw output is not published; it stays in the run store behind its explicit reader.

The pure `story-stage-deliveries` Session projection groups recorded paths by the actual Story tool call ID. The Client cards for write, update, revise and resume subscribe through `useProjection`, retain committed versions while the call runs, and use the existing `openFile` action. The cards do not infer paths, automatically switch the document being read, or erase historical deliveries of other kinds. The generic publisher supports explicit artifact publication only; the four-kind selection belongs to the runner.

Publication uses the existing known Session event and native tool policy. It adds neither a fabricated model tool call nor an unrecognized Session event. Committed delivery identity is reconstructed from the log, and repeated publication within the same owning call checks the same file before reusing its event. A resumed call can show retained eligible versions under its own card while reusing completed native stage output. A cached blocking collection review may drive resumed repair only when the latest persisted domain review exactly matches that saved response. Its eligible settings collection can be displayed; the review stays internal. Raw output without such an admitted review returns through normal admission and bounded review repair; rejected output is not published.
